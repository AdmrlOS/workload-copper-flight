# Customer guide: native flight, visible evidence

## What runs where

| Component | Executes on | What it establishes |
|---|---|---|
| Vehicle physics, forest scene, stereo/depth generation | Native edge process (`quad-sim`, Bevy) | Simulated observations and actual simulated vehicle state—not a physical sensor/drone |
| MCU/control and compute/autonomy graphs, ViTFly model | Native edge process (Copper) | Learned policy execution with the observed CPU/CUDA backend |
| Supervisor, persistence and read-only HTTP API | Edge workload | Episode supervision, bounded recordings, telemetry and packaged UI |
| 3D scene, camera navigation, pose interpolation, recorded timeline | Customer browser (WebGL) | Visualization of native observations—not simulation, policy inference or CUDA in the browser |

Headless means no display surface/compositor is required; native graphics are still required to generate the simulated depth input. Browser WebGL success does not prove NVIDIA Vulkan or CUDA. There is no physical-drone actuation interface.

The source chain is inspectable: [Dockerfile](../Dockerfile) selects `vitfly-cuda,forest-world,autonomous-demo`, CUDA 12.6 and compute capability 87; [source lock](../native-source.lock.json) pins Copper `d46ef87a65c7ba93bcad3c236da99e52cd77f319`; prepared `components/tasks/cu_vitfly/src/task.rs` selects a real device, uploads depth/attitude/speed tensors, calls `model.forward` and downloads the prediction. [Native status](../patches/native_status.rs) observes the loaded backend and Bevy adapter rather than deriving them from requested flags. This is source evidence; execution on the delivered image must separately pass [acceptance](ACCEPTANCE.md).

## Live, Recorded and depth

- **Live** follows newly observed native telemetry. The browser may buffer/interpolate between observed poses for presentation; it must not extrapolate a mission or conceal a stalled source. Native sample cadence, simulation-time/wall-time ratio and browser render rate are different measurements.
- **Recorded** opens a completed mission's saved telemetry and advances a visualization clock. Scrubbing or selecting 1× playback does not run the flight graph again and says nothing about original execution speed.
- **Native flight replay is NOT IMPLEMENTED.** Neither downloaded Copper files nor browser playback demonstrate deterministic recomputation, output equality or replay integrity.
- **Depth is simulated**, generated by native Bevy rendering and consumed by the Copper simulated ZED source—not a physical ZED feed. The optional preview is a quantized 32×24 sampling of an actual completed 320×240 depth buffer. It is not an RGB camera, full-resolution capture or synthetic browser-generated image. Source millimetres, displayed metres, invalid pixels and sample age must remain explicit. Cached preview repetitions are not new sensor frames. CPU sampling timestamps are not camera acquisition timestamps; acquisition time is unavailable.

Final-device depth/UI acceptance remains **PENDING** until the exact release is exercised. Older recordings may legitimately have no depth preview; show unavailable, not invented pixels.

## Choose recording policy explicitly

| Setting | Preserved | Deliberately omitted | Suitable for |
|---|---|---|---|
| `FLIGHT_NATIVE_LOG_MODE=full` (native default) | Actual graph/model/scene, native telemetry, controller + compute Copper binary log families and task-state keyframes | Nothing intentionally disabled by this mode | Inspectable full capture; must budget substantial storage and I/O |
| `FLIGHT_NATIVE_LOG_MODE=telemetry-only` | Same graph/model/scene and selected inference backend; native pose/policy observations and optional preview | Binary CopperLists and task-state keyframe recording | Lower-I/O live demo and recorded **telemetry visualization**, not a full recording/replay archive |

Removing binary logging removes work and evidence, not just file downloads. It does not guarantee realtime operation. Do not label telemetry-only as full recording. Read the observed `frame.copper.recording_mode`/`full_recording`; do not infer mode from a Configuration label. [Contract](../native-contract.md) defines clocks and fields.

Runs persist under `/data/copper-flight`; map `/data` to workload persistent storage. Keep free space and retention appropriate to the measured mode and episode duration. Native slabs can preallocate significant logical space. Replacing the workload image must not replace run storage.

## Build prerequisites and reproducible inputs

This is a Linux **ARM64** workload. A generic x86 GitHub runner can test service/UI code but cannot certify Jetson GPU operation.

1. Use Docker Buildx/BuildKit capable of Linux ARM64 builds (native ARM64 preferred), adequate memory/disk for Rust/CUDA builds, and build-time network access for pinned upstream/assets/packages. Runtime scene/model access is packaged locally; offline operation still needs its own acceptance.
2. Preserve `Cargo.lock`, [source lock](../native-source.lock.json), [asset lock](../native-assets.lock.json), the complete native patch stack, [graphics lock](../graphics/payload.lock.json) and probe lockfile. Hashes are integrity evidence, **not redistribution permission**. Obtain scene/model/font/vendor rights approval before distributing a populated image.
3. Supply the exact two NVIDIA package archives identified in `graphics/payload.lock.json`, in an approved local directory. Their graphics userspace must match the target runtime's injected driver profile. Current lock: L4T `39.2.1`, package `39.2.1-20260806224157`, driver `595.78`, profile `tegra234-nvgpu-r39.2.1-v1`. Do not silently substitute packages or overwrite injected driver libraries.
4. Supply a Linux ARM64 `copper-vulkan-depth-probe` built from `graphics/probe/`. It is a required named build context, not a binary supplied by a source checkout.

Example clean source-build route (run from repository root; directories are customer-supplied):

```sh
export GRAPHICS_DEBS_DIR=/absolute/path/to/approved-matching-debs
export PROBE_BINARY_DIR=/absolute/path/to/probe-output
mkdir -p "$PROBE_BINARY_DIR"
python3 scripts/native_sources.py prepare --source upstream

docker buildx build --load --platform linux/arm64 \
  --target native-toolchain -t copper-flight-toolchain:local .
docker run --rm --platform linux/arm64 \
  -v "$PWD/graphics/probe:/probe:ro" -v "$PROBE_BINARY_DIR:/out" \
  -w /probe --entrypoint cargo copper-flight-toolchain:local \
  build --locked --release --target-dir /out
# Dockerfile expects the probe at the root of the named context.
cp "$PROBE_BINARY_DIR/release/copper-vulkan-depth-probe" "$PROBE_BINARY_DIR/copper-vulkan-depth-probe"

docker buildx build --load --platform linux/arm64 --target flight \
  --build-arg IMAGE_REVISION="$(git rev-parse HEAD)" \
  --build-context graphics-debs="$GRAPHICS_DEBS_DIR" \
  --build-context probe-binary="$PROBE_BINARY_DIR" \
  -t copper-flight:local .
```

The default `native` stage compiles the CUDA simulator from pinned patched sources; no prebuilt private simulator binary is necessary on this route. `native-local-cuda` instead requires an explicitly supplied `native-binary` context containing `quad-sim-cuda`; it is an alternative packaging route, not the source-only default. First builds need package/asset access; apt repositories are not snapshot-locked, so record resolved package inventory and exact output digest rather than promise bit-for-bit rebuilds. A dirty worktree must not be labeled as the committed revision without an accompanying source manifest.

These are build prerequisites/instructions, not a claim that a fresh customer environment was built in this documentation pass. Record the actual command, source manifest, native binary hash, image digest and target acceptance for each delivered release.

## Deployment and off-network access

Have your Admiral administrator create a customer-scoped Configuration using an immutable image digest, a **reference** to your approved registry credential, persistent `/data`, headless mode and explicit inference/recording policy. Do not reuse IDs or credentials from another deployment. Build/publish, Configuration creation and fleet rollout are separate approved operations; save the prior selected Configuration for rollback and canary one device first.

The selected Configuration must advertise the named EdgeWire service:

```yaml
spec:
  edgewire:
    services:
      - name: web
        protocol: tcp
        port: 8080
```

This fragment is the service requirement, not a complete Configuration create-request schema. TCP port publication alone does not create an EdgeWire named target. Preserve current developer-session/access policy and verify the selected Configuration after changes.

With the Admiral CLI already authenticated for the customer's scope:

```sh
export ADMRL_ORG='<customer-organization>'
export ADMRL_DEVICE='<approved-customer-device>'
admrl edgewire forward --org "$ADMRL_ORG" --no-login \
  "$ADMRL_DEVICE" web 127.0.0.1:18083
# Leave the forward running; in another terminal:
curl --fail --max-time 10 http://127.0.0.1:18083/api/state
curl --fail --max-time 10 --output /dev/null http://127.0.0.1:18083/
```

Open `http://127.0.0.1:18083/`. The authenticated tunnel supports off-network access; a LAN IP is not required. Use target **`web`**, not `8080`. Keep the local listener loopback-only; the app's read-only API is not a substitute for access control. An established tunnel alone is not application acceptance: verify both API response and rendered page. Never include credentials in URLs, shell history, screenshots or source exports.

## Value beyond one device—workflow, not a scale benchmark

The same pinned workload and evidence contract can support a repeatable rollout workflow: canary an immutable image; compare observed backends and source freshness; preserve mission provenance; inspect completed telemetry; bound capture storage; and promote or roll back an approved Configuration. This separates autonomy development from per-device packaging and makes fleet troubleshooting more consistent.

**Fleet scaling is UNVERIFIED.** No concurrent-device benchmark, aggregate tunnel/session test, rollout-capacity test, storage service-level objective or fleet-wide throughput result is established here. Measure these on the intended topology, hardware and recording policy before making capacity or cost claims. [Acceptance](ACCEPTANCE.md) separates earlier one-device observations from pending final-release results.
